# 데이터·보안 점검 (2026-11-07)

사람이 늘어나기 전에 데이터 구조와 보안을 한 번 훑었다. 웹 API·DB·실시간 서버를 나눠 코드를 읽고, 운영 DB에는 공개 키로만 바깥에서 두드려 봤다.
고친 것은 테스트(220개)와 개발 서버에서 확인했다. 남은 일은 아래 "남은 일"에 우선순위로 적었다.

## 안전하다고 확인한 것

- **DB가 브라우저에 열려 있지 않다**: 공개 키(브라우저에 들어 있는 키)로 운영 DB의 24개 표를 모두 읽어 봤더니 0줄 (RLS가 모든 표에 켜져 있고 정책이 없다). 공개 함수·뷰도 없다. 서버만 DB에 직접 붙는다.
- **운영자 기능**: 운영자 확인을 데이터보다 먼저 한다. 운영자가 아니면 없는 주소처럼 404.
- **남의 것 건드리기(IDOR)**: 기록·방명록·사진·점포를 바꾸거나 지울 때 서버가 주인을 확인한다.
- **오류 메시지**: DB 오류·내부 내용을 화면에 내보내지 않는다.
- **글자 그리기**: 사용자가 쓴 글을 HTML로 넣는 곳이 없다 (XSS 통로 없음).
- **실시간 서버**: 입장 토큰·공지 서명을 시간차 공격에 안전하게 비교하고 만료를 본다. 웹소켓 메시지 크기·횟수 제한, 운영자 명령은 서명된 토큰에만.

## 남은 일 (우선순위)

### 사람이 늘기 전에
1. **사진을 Supabase Storage로 옮기기**: 지금은 DB에 들어간다. 상한을 뒀지만 사람이 늘면 DB 용량(무료 500MB)이 먼저 찬다.
2. **가입 봇 막기 (CAPTCHA)**: 메일 인증을 꺼 둬서 스크립트로 계정을 마구 만들 수 있다 (토론 표·대항전 점수 부풀리기). Supabase Auth의 CAPTCHA(Cloudflare Turnstile, 무료)를 켜고 가입 화면에 붙인다. `[결정 필요]` 사이트 키 발급.
3. **메일 발송 서비스(SMTP) 연결 뒤 Confirm email 다시 켜기**: 지금은 아무 이메일 주소로나 가입할 수 있다 (남의 주소 선점).
4. **Supabase 대시보드 비밀번호 규칙**: Authentication → Policies(Password)에서 최소 길이 8 (화면은 8자를 요구하지만 서버 기본값은 6).
5. **`CRON_SECRET`**: Vercel 환경변수에 넣어야 매일 정리 작업이 돈다 (없으면 정리가 안 된다).

### 사람이 늘어나면
6. **차단을 실시간 서버에서도**: 지금은 화면이 숨긴다. 화면을 고친 사람은 나를 차단한 사람의 위치를 볼 수 있고, 숨김 목록으로 누가 나를 차단했는지 짐작할 수 있다. 실시간 서버가 서로 보이지 않게 거르도록 (StateView).
7. **마을 집 목록을 동네 단위로**: 지금은 모든 주민의 집을 한 번에 보낸다 (5천 명쯤부터 무거워진다).
8. **횟수 제한을 서버 전체로**: 지금은 서버 인스턴스마다 센다. 남용이 보이면 Redis(Upstash)나 DB 표로.
9. **추천 점수 되풀이**: 추천을 껐다 켜면 대항전 점수가 또 들어간다 (하루 상한 20점 안). 한 논거에 한 번만 주도록 기록 표를 둔다.
10. **사진 정리**: 어디에도 쓰지 않는 사진을 자동으로 지우지는 않는다 (상한으로 막는다). 사진 고르기 목록에서 사라지면 놀랄 수 있어 두었다.

### 작은 것
- 걷기 검사가 도착점만 본다 (3.5칸 안에서 울타리를 건너뛸 수 있다). 지금은 위치가 보상과 이어져 있지 않다.
- 낚시·열매는 위치를 확인하지 않는다 (하루 상한·대항전 상한은 있다).
- 지운 논거 글이 지난 경기 결과의 대표 논거 칸에 남는다.
- 실시간 서버 CORS가 모든 사이트를 허용한다 (쿠키를 안 써서 직접 피해는 없다).
